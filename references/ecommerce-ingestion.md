# 电商知识库：一到二、二到三入库标准

本文件只适用于用户的跨平台电商知识库，且只定义电商 profile 的模板、分类法、
平台路由和领域边界。公共的一到二、二到三、结构化去重、门禁、同步、验收、失败续传
和缓存清理由 `SKILL.md` 的统一状态机负责；不得在本文复制或另建一套电商流程。
本文件不自动启动加工，也不把一次批次的数量、样本数、运行时长、API 配额或故障现象
写成长期门槛。

## 1. 分层、路线与目标

| 层级 | 保存什么 | 不承担什么 |
|---|---|---|
| 一层 | 原视频、音频、图文、原始转录、来源登记与版本 | 不用摘要替换原件 |
| 二层 | 来源母卡、结构化知识点、证据和条件；由其生成阅读卡与主题索引 | 不把整理推断变成作者主张，不强制每来源产出知识点 |
| 三层 | 给 AI 使用的、能独立回答具体问题的紧凑知识单元 | 不搬运全篇原稿或审计记录，不凭空补出综合诊断与建议 |

先选择用户本次授权的路线：

- `ECOM_L1_TO_L2`：盘点一层 → 语义提炼 → 二层暂存 → 检查/抽检 → 备份发布二层与索引；到此停止。
- `ECOM_L2_TO_L3`：二层只读 → 复用索引与已审内容 → 准入/归并 → 三层预览 → 检查/抽检 → 经授权发布 Dify → 实际检索抽测。
- 两段联动：用户明确要一到三或两段一起做时，顺序衔接以上两段。
- 仅讨论、设计、预览或改 Skill：不发布正式二层、不写 Dify，也不顺带重建向量。

当前电商二层入口为 `./example-vault\电商知识库`，从其 `_meta/manifest.json`
和现有结构、阅读映射索引定位资料；一层来源位置从登记清单读取，不扫描无关磁盘。
过程产物放在 `D:\自媒体\05_工程过程归档`，报告放在 `D:\自媒体\04_分析预览与验收`。
Dify 使用本次已授权的独立电商目标，以运行回执中的精确 dataset/document ID 为准，
不能凭相似名称或示例 ID 认定目标；不明时询问。旧京东运营诊断库及其他库保持不变。

写入前核定本次范围、权限、目标、输入版本、可恢复快照和唯一写入者。
这些是写入安全检查，不等于每批先调用模型探活。用户未要求时不新增固定模型预检步骤。

通用二层渲染器必须显式使用 `--profile ecommerce`。短视频母卡进入 `02_知识卡片`，
长课程母卡进入 `03_课程笔记`；不得沿用 GEO/AI 目录。渲染结果必须带 YAML 原生布尔
`eligible_for_l3: true`、`note_type: source_master`，并让卡片与 staged manifest 的
`source_unit_id`、`idempotency_key` 完全一致，之后才能交给三层读取契约。

### 运行默认值

- `ECOM_L1_TO_L2` 与 `ECOM_L2_TO_L3` 的默认生成模型为 `gpt-6-luna`，默认推理强度为高（`reasoning_effort=high`）。
  默认并发为 8 路，但仅用于批次内相互独立的语义提炼与改写（map 阶段）。
- 用户当次明确指定其他模型或并发时，在任务级覆盖默认值；不要把当前默认写成永久排他的模型禁令。
- 哈希、稳定身份、结构排除、本地文本召回、投影、校验、统计和同步使用确定性程序，不调用生成模型。
- 全局跨批去重、灰区合并决定和共享 atom 映射由主任务在 reduce 阶段统一收敛，
  不得并发修改共享合并状态；Dify 保持唯一正式写入者。

## 2. 电商博主发现、下载与转录

本段只在用户明确要求寻找、筛选或导入电商博主时启用。Better Douyin 等工具只是发现入口，
不能仅凭昵称、简介或单条标题判定作者是否属于电商语料。

1. 读取新增博主清单并进入主页抽看代表作品，按实际内容判断：平台运营、选品商品、投放、
   供应链履约、客服售后、交易合规、经营管理或电商工具属于相关内容；泛自媒体、生活记录、
   情绪表达和通用 AI 内容若没有直接电商用途，不纳入。混合型博主只纳入电商相关作品。
2. 保存作者级筛选账本：作者身份、主页、检查时间、代表作品证据、`纳入/排除/待确认` 和理由。
   “待确认”不自动下载全量，也不冒充已筛选完成。
3. 用户要求全量下载时，先分页建立范围内作品清单，再按清单下载；记录作品 ID/URL、标题、
   发布时间、置顶/重复关系、媒体文件、字幕或文案、下载状态及失败原因。全量指已纳入作者在
   本次范围内可访问的全部作品，不等于扫描无关磁盘或下载非电商作品。
4. 保留原视频、原字幕和页面文案，不覆盖原件。可验证的原字幕优先作为转录来源；缺字幕的
   视频再转录。完全无法识别的作品按用户约定跳过并记账，不猜写正文；局部疑词保留原词和
   时间位置，不因此丢弃整条可用内容。
5. 短视频以一条作品为一个来源单元，用作品 ID、URL 和 ASR 时间区间定位；长课程按课程、章节、
   课节和时间区间组织，不能按文本行号切分或定位。文件换行变化不得破坏溯源。
6. 每个来源转录稳定后即可进入一到二暂存；整批联动入三层时，默认等授权范围内二层全部完成并
   通过抽检后再统一生成三层，避免反复同步和重复建向量。同步模式由公共 run-level 参数决定，
   默认 `segment_incremental`，也可显式选择 `full_document_replace`。

筛选、清单、下载和转录各自报告实际数量与失败项；看到文件、启动转录或完成部分作者均不算
全量完成。

## 3. 一层 → 二层：来源保真

### 覆盖与原文

- 每个纳入范围的来源都有唯一去向：新增、版本更新、重复来源映射、零知识点、已授权跳过或失败。
- 原件与原始转录不覆盖。完整语境保存在可访问的一层/来源归档；二层提供稳定链接和就近证据。
  无法定位一层原件的旧资料，保留现有归档全文并登记缺项，不能只剩摘要或失效链接。
- 一份可用来源对应一张来源母卡，可含零到多个知识点，不按视频数凑知识点数。
  已获准跳过的整条无有效转录材料记录原因、保留原文件，不重转、不当制卡失败。
  可读稿内局部疑词不等于整条跳过；生活、广告等无可用内容如实记账。
- 语义提炼阅读完整来源，不能只取开头、固定字数或正则套句。长内容按章节/说话者和上下文处理，
  必要时分请求并回并到同一来源身份；不能把后半段独立问题遗漏。
- 本次只授权文本时，不自行把目录里的所有图片也算作品入库。图文需先按作品归组，
  保留页序和图像证据；OCR、听音和看画面的复核状态分别记录。

### 来源、版本与证据

- 来源 ID、`card_id`、`point_id`、证据 ID 稳定；标题、顺序、作者昵称改变不换 ID。
  已有作品 ID 按平台和作品身份登记；否则使用已登记的本地来源身份。
  源哈希标识版本，校正转录不应自动创建新母卡。保留旧 ID/旧路径到新展示路径的映射。
- 每个实质主张关联原文摘录及实际段落、章节、页序或 ASR 时间区间，保留来源路径、哈希/修订。
  粗时间段不能编成秒级精度；只读文本不能标为已听音或已看画面。
- 摘录保留原字样。术语修订另记原词、改词及确认依据，不全库猜同音词或悄悄改证据。
- `source_statement` 与 `editorial_note` 分开；作者步骤、指标、前提、止损中只放来源明确支持的内容。
  编辑提示必须标出其性质，不能出现在“作者说了什么”的字段或摘要中冒充来源。
- 缺项区分 `not_provided`、`not_applicable`、`unclear`、`pending_review`；不让空数组同时表示已查无问题和未查。
  摘录准确、来源意见一致、外部核验通过是不同状态。

### 平台、数字与时间

- 分开 `source_platform`（作品发布平台）、`subject_platforms`（实际讨论平台）及推广工具。
  抖音上讲淘宝不归抖音电商；快车、直通车不视为同一实体。平台或工具不明时保留未明确状态。
- 可迁移性须绑定具体主张、平台和证据；多个作者说法相同，不等于跨平台通用或规则已核验。
- 数字保留原区间、原话、单位、对象和性质：演示例子、作者建议、个案结果、规则声称、已核验规则。
  来源没写的单位、日/月周期、百分比、样本量不补写；个案数字不升格为统一阈值。
- 指标保留已知的分子/分母、统计/归因窗口、退款口径和数据对象；口径不明的 ROI、ROAS、投产不可直接互换。
  整理者计算另记公式、输入与依据，不改成作者原话。
- 区分发布时间、讨论时期、采集时间和核验时间；标题年份和下载时间均不冒充发布时间。
  旧规则、功能、处罚和后台入口标注时效边界，未核验不等于现行有效。
- 关键步骤依赖缺失画面或听不清的对象时，明确标注依赖；保留原始资料但不包装成完整教程。

## 4. 二层卡片类型、主题与展示

底层共用来源、身份、证据与版本契约；阅读结构按内容选择，不全库套一个固定正文模板。
默认一个主类型；副类型须有独立知识点或模块支持，不因出现数字或设置按钮就加标签。

| 主类型 | 按来源实际存在的内容组织 |
|---|---|
| 诊断判断 | 问题/现象、排查依据、条件分支、动作与判断边界 |
| 方法流程 | 适用前提、有顺序的步骤、观察指标、调整或退出条件 |
| 指标口径 | 指标定义、计算口径、数值性质、统计窗口与使用限制 |
| 规则功能 | 平台/产品/版本、功能或规则声称、操作入口与核验状态 |
| 案例复盘 | 背景、动作、结果、已知条件与不可推广的部分 |
| 观点策略 | 核心主张、依据、适用范围与反例/局限 |
| 风险提醒 | 风险情形、证据、后果及来源支持的处理边界 |

栏目按内容存在与否出现，缺少步骤、因果或止损就明确缺项，不为凑类型补写。
独立问题可分知识点；同一流程及其互斥分支保留关系，不拆成失去条件的孤句。
混合稿按模块组织，不强制整篇只有一种形状，也不升级成大型流程引擎。

首屏应能读到具体问题、来源要点、平台/对象和关键限制；证据就近，技术字段折叠或入元数据。
摘要和标题不比原文更确定，不猜术语、不补单位、不把编辑建议写成作者结论。

- 中文文件名、主副标题、目录、图谱节点和索引显示有意义的主题，不显示 JD/NB 等内部编号。
  编号保留在内部索引、元数据、溯源字段，不能为隐藏编号删掉机器身份。
- 保留可用总索引、主题 Hub、具体问题入口、作者/来源辅助索引和双向来源映射；
  索引仍可打开，不把“隐藏技术节点”误做删除索引。沿用已批准的图谱配置，不顺带重置插件。
- 业务主题与卡片类型分开。复用正式主题词表：选品商品基建、新品生命周期、自然搜索、付费推广、
  人群、点击转化、成本投产、异常恢复、供应链与库存履约、客服售后与交易风险、经营模式与团队管理。
  用具体问题入口细化宽主题；确有新业务主题可有依据地补充，不按固定数量强塞，也允许待分类。
- 同卡可链接多个主题但不复制多份正文。不同来源的母卡保留；确认等价的观点可在阅读展示层归并，
  每个知识点的条件、独有内容和来源仍可回查。相似度只召回候选，不直接授权归并。
- 改名/归并后更新实际链接、旧路径映射、去向与计数；中文改名不触发重新语义生成。
  二层关系向量是独立索引，已有就沿用；非本次授权不切模型或全库重嵌入，更不自动套 GEO 的智谱设置。

### 二层向量输入边界

- 二层发布不得自动触发向量化。只有用户当次明确要求二层关系索引时，才准备独立向量任务。
- 完整原稿、完整转录、原稿附录和长篇证据引用永远不得作为二层向量输入。
  二层关系索引仅使用标题、摘要、结构化知识点、平台、对象、条件和边界等派生字段白名单。
- 白名单不能只检查字段名。调用前以确定性程序校验单字段和总载荷长度、与完整原稿的
  长连续片段重合及原文覆盖比例，防止原稿被误塞进 `summary`、`key_points` 等白名单字段。
- 校验不通过时拒绝该向量请求、记录原因并停止在向量调用之前；不静默截断，不先跑后查。
  若当前工具不能证明已排除原稿，同样不启动二层向量化。
- 三层 Dify 只对已准入的紧凑 atom 建立检索向量，不反向要求二层原稿向量化。

## 5. 二层 → 三层：轻量加工与准入

先读 manifest、知识点索引、阅读映射和已有三层来源映射/合并决定。
已确认且源版本未变的二层知识点及三层预览可以复用，程序负责转换和校验；
只回源处理新内容、变更、疑点和会影响边界的合并，不重新全库抽取或全量逐卡人工复审。
二层摘要和分类只辅助定位，最终实质主张必须能回到原文证据。

每条三层知识回答一个具体问题，正文包含完整主张/动作、适用条件与来源边界。
同一判断的必要分支和完整步骤应一起保留；一个来源可以贡献零到多条，不凑固定数量。

| 处理结果 | 条件 |
|---|---|
| 新增/更新 | 可独立使用、关键内容有证据、必要边界明确 |
| 合并/增加来源 | 问题、对象、方向、条件、用途与边界等价；保留各来源 |
| 关联但不合并 | 条件不同、平台不同、版本不同、互补或冲突；分别保留差异 |
| 仅留二层 | 关键对象/动作/术语无法识别、重要画面缺失、语义残片、泛泛表达或仅风险留档 |

合并不平均数字、不拼成来源未给出的统一策略；作者重复不算多个独立证据，转载关系未明不声称独立共识。
来源经验不升格为现行政策。失效/替代知识退出活跃投影并保留修订映射和恢复记录。
风险材料可保留警示与边界，但不把来源中的不当操作包装成推荐执行步骤。
确需新增综合建议或跨来源诊断时，另有明确任务和证据分层；不把普通入库扩成重型知识工程。

生成、语义改写和灰区合并判断使用用户当次指定的模型；未另指定时使用 `gpt-6-luna`。
默认并发为 8 路且仅用于相互独立的提炼与改写 map 阶段；全局去重、合并与映射由主任务在
reduce 阶段统一处理。确定性代码负责投影、哈希、组装、去向、索引、校验和同步，
不能以关键词占位或机械截断冒充语义提炼；向量模型只负责索引和召回。

知识去重采用轻量混合路线：先用稳定身份、内容哈希和结构化指纹处理确定重复；再按平台、对象、
问题、阶段、条件、方向和风险边界排除明显不能合并的记录；只在兼容分区内用问题键与本地文本检索
召回少量 Top-K，已有且兼容的向量索引可以补充召回，但不得为了去重新建、重建或批量补做向量。
向量和文本分数都不直接授权合并。确定等价的记录合并并累计来源，确定有差异的直接分开，
只有少量灰区交给生成模型审查紧凑字段。问题键、本地文本和可选的已有兼容向量都没有候选时，
保守归为独立新增；不得触发临时建向量、扩大扫描或全量模型比较。不得做全量两两文本比较或全量模型审核。

允许并行处理时，子任务只处理独占批次及必要自检，主任务负责分工、统一合并、抽检和唯一正式写入。
每批记录已完成/跳过/失败/剩余，不在修复一条后漏掉余下清单；不自动无限增开任务或承诺固定完工时长。

## 6. 三层投影与 Dify

三层优先给 AI 检索使用。内部结构至少能追溯稳定 atom ID、来源卡及其版本/哈希、知识点、证据定位；
复用当前正式 schema 和已验证投影，不另起不兼容字段体系。

每个可返回的完整知识块按以下顺序保持可读：

1. 自然中文主题标题；不加内部编号。
2. 实际讨论平台与具体问题；必要时保留原始平台/工具范围。
3. 知识要点：完整结论、动作或分支。
4. 适用条件、限制、未确认项；来源经验与现行规则核验状态分明。
5. 来源标题和溯源标识；经本地索引可定位母卡、点和证据。

别名/相关问法仅在真实同义时补充，不灌入猜测关键词。完整原文、原始 JSON、审计记录、
批次日志、排除清单及长来源数组不进入检索正文；这些留在维护与恢复产物中。

按实际讨论平台维护少量平台文档，例如京东、淘宝天猫、抖音电商；具体文档名单由本批索引决定，
不固定份数，不按作者、卡片类型或每条来源拆成海量文档。归一后保留原讨论范围。
“跨平台比较”单独保留比较边界；“通用电商”需要有平台无关的依据；
“平台未明确”是未知，不自动变成通用，也不强塞给作品发布平台。

一条独立知识保持一个完整可返回父段。短知识已经紧凑完整时，子块可以等于父块；
不硬套 GEO/AI 的 200～300-token 分拆，也不强拆成缺条件的数字或动作。
超长时再按实际模型限制处理，保证命中后返回完整上下文；具体参数复用本库已验证规则。
不可为提速永久改成整个平台一个巨型父段。临时索引实验须在验收前恢复并核对。

文档记录 `platform` 等已使用的元数据。分类不等于应用会自动过滤：实际检索测试需验证显式平台筛选，
比较问题可包含跨平台比较；未知平台材料不能当成确定的平台操作规则。
本任务未获授权时不改生产应用、凭据或供应商配置。

### 电商目标文档路由

平台与目标文档的匹配规则维护在 `profiles/ecommerce.json`。公共流水线先按
`subject_platform` 路由，再执行当次选定的通用同步模式。默认 `segment_incremental`
以稳定 `atom_id` 为粒度，通过 Dify 文档段落接口继续复用原 dataset ID 和 document ID：

- 新 atom：调用新增段落接口，只为新增段落建立向量；
- 已有 atom 的正文、边界、来源或版本发生变化：按已登记的 segment ID 调用更新段落接口，
  只重建受影响段落；
- 内容和来源版本均未变化：跳过，不发写请求；
- atom 失效或被替代：先保留恢复记录和替代关系，再按 Dify 实际能力停用对应段落；
  需要删除时须取得当次明确授权，不借“增量同步”顺带删除；
- 单次部分失败：按 atom/segment 记录成功、失败和重试状态，使用幂等键续传，不重放已成功段落。

维护 `atom_id ↔ segment_id ↔ content_hash ↔ source_version` 的持久映射和远端基线标记。
写入前比较远端基线；写入后重新读取受影响段落，核对 ID、哈希、启用状态和数量。
基线漂移、映射冲突、同一 atom 对应多个活跃段落或另一写入者正在工作时停止写入。

选择增量模式时不得重新生成并上传整个平台 TXT，不得通过“更新文件”接口覆盖完整文档，
也不得因部分接口失败新建 `京东-02`、`京东-03` 等替代文档。TXT 可以作为首次迁移、备份或
人工恢复材料，但不是后续增量同步通道。若旧文档缺少可可靠恢复的 atom/segment 映射，先输出
一次性迁移方案和预览；只有用户明确授权迁移后，才能建立段落基线。没有正式平台文档时，
新增平台可在当前授权范围内创建一次文档，随后全部走段落接口。

上传前保存目标快照、哈希和写入回执，核对没有其他写入者或基线漂移；结果不确定时先查询远端，
不盲目重传或创建替代库。模型选择沿用本次已授权配置，不固定某个供应商。

选择 `segment_incremental` 时，正式写入使用本 Skill 的 `scripts/sync_dify_segments.py`；它只接受
`new/update/skip/failed-resume` 四类结果，持久化每个成功 atom 后再继续，并在写后回读。
真实传输适配器不得把密钥写入命令、映射或回执。`lv-dify` 继续只读，不是写入通道。

## 7. 检查、抽检、恢复与完成定义

全量程序检查只做确定性项目：范围去向、源哈希、稳定身份、点/证据引用、原文定位、
双向映射、重名/断链、主题/平台归类字段、`atom_id ↔ segment_id` 映射唯一性、增量去向统计、
最终数量及远端受影响段一致性；不冒充全量语义或事实验收。

二层提交与三层发布使用分开的门：`stage_gate.py check-layer2-commit` 只检查二层验证、
正式 manifest 基线和可恢复快照；`check-layer3-publish` 才检查比较完成与 Dify 基线。
旧 `check-commit` 是三层门的兼容别名，不能拿它阻塞二层提交。
人工按来源、平台、类型、长度和风险分层抽检，疑点定向扩查；不固定每批先做样板批准，也不改成全量人工验收。

明确分开五种状态：二层发布、二层关系索引、三层正文上传、三层向量完成、真实检索抽测完成。
Dify 抽测使用实际口语/语义问题，检查返回内容、平台筛选和条件/来源完整性；
不能以本地关键词、精确 ID、上传成功或“模型可用”标志代替召回测试。
精确目标 ID 未命中需读结果判断是否等价，抽测结果不宣称全库召回率或应用最终回答质量。

沿用已有样本和验收结果时绑定内容哈希，变更相关项需重新检查；批次统计从最终产物重算。
只有本次承诺的各阶段实际完成，才能报“全量完成”；只完成正文时如实报部分完成。

故障处理限定为已发生的故障：分钟限速或临时不可用可退避后续建；每日额度耗尽、身份不明、
权限不足、服务离线或需要新的付费/凭据决定时，保留现场并报告需要什么，不无休止重试。
不把偶发故障变成每批固定模型探活；不自行换令牌、切模型、购买额度或重启 NAS。

本电商 profile 保留用于维护和恢复的原子、投影、双向来源索引、去向、哈希、写入回执与抽测记录；
它们是构建与追溯产物，不是第二个独立维护的正式三层库。临时构建缓存按 `SKILL.md`
统一清理；压缩恢复包、幂等映射和最小回执作为恢复资产保留。
删除仅在用户另行批准的明确范围内进行；中断时不删除恢复材料，恢复后核对输入与远端再续做未完成部分。

## 8. 一个贯穿两段的例子

来源在抖音发布，实际讨论淘宝，原文只有：“人群预算先放50到100，后面再看”。

- 一到二：保留完整原话与来源，问题可写“淘宝人群预算的起始设置还缺哪些条件”；
  标注单位、周期、具体人群和后续判断标准未提供。不能写成“每天50～100元低预算测试”。
- 二到三：此例关键配置缺失，去掉数字也没有可独立使用的具体方法，仅留二层并记原因；
  不把该条跳过扩大为整份可读来源丢弃，不阻塞同批其他合格点。
- 若后来回源补齐条件：修订原母卡和受影响知识点，保留原身份；仅在二层修改获授权时更新二层，
  二到三任务本身不顺带改原卡。随后按新版本生成/更新对应三层单元，不重做全库。
